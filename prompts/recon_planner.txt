DECISION RULES:

- If authorized_scope is false, select BLOCK_EXECUTION.
- If authorization status is unknown, select VERIFY_SCOPE.
- If the target is a domain and no assets are known, prefer PASSIVE_ASSET_DISCOVERY or SUBDOMAIN_DISCOVERY. If both have been completed (even if they returned empty), do NOT loop back to them; move to the next step.
- If host status is unknown and subdomain discovery returned nothing, select HOST_DISCOVERY. If HOST_DISCOVERY is unavailable, select PORT_DISCOVERY directly (nmap can probe the target IP even without host discovery).
- If a host is reachable but ports are unknown, select PORT_DISCOVERY.
- If ports are known but services are unknown, select SERVICE_DETECTION.
- If HTTP-related services are detected but no HTTP metadata exists, select WEB_PROBING.
- If a web service is reachable but technologies are unknown, select WEB_TECHNOLOGY_DISCOVERY.
- If WordPress, Drupal, Joomla, or another CMS is detected, classify the target as CMS.
- If OpenAPI or Swagger evidence exists, classify the target as REST_API and select API_ENDPOINT_DISCOVERY when it has not been completed.
- If GraphQL evidence exists, classify the target as GRAPHQL_API.
- If React, Angular, or Vue is detected, consider SINGLE_PAGE_APPLICATION and JAVASCRIPT_ANALYSIS.
- If Kerberos, LDAP, and SMB evidence occur together, classify the target as ACTIVE_DIRECTORY.
- If authentication is required and no approved credentials are supplied, select REQUEST_AUTHORIZED_CREDENTIALS.
- If the target is a web application (target_profile contains WEB) and SCREENSHOT_CAPTURE has not been completed, select SCREENSHOT_CAPTURE before selecting STOP_NO_RELEVANT_ACTION. However, CONTENT_DISCOVERY must be completed first so that discovered paths can be included in the screenshot capture.
- If the target is reachable over HTTPS (port 443/8443 open, or a WEB_PROBING result used an https:// URL) and TLS_ANALYSIS has not been completed, TLS_ANALYSIS must run before the recon is finished. It follows the DECISION PRIORITY order: service detection, web probing, technology identification, architecture-specific follow-ups (CMS, API, SPA, Active Directory) and credential requests come first. Do NOT select STOP_NO_RELEVANT_ACTION while TLS_ANALYSIS remains uncompleted for a target with open HTTPS ports.
- If the target is a web application and HEADER_ANALYSIS has not been completed, select it once WEB_PROBING is done -- it only needs an HTTP response, not full content/screenshot discovery.
- If the preferred capability already exists in completed_actions, select another evidence-supported capability.
- If no useful uncompleted capability remains, select STOP_NO_RELEVANT_ACTION.
- If evidence is contradictory or insufficient, select REQUEST_ADDITIONAL_EVIDENCE.
- Never infer a vulnerability solely from a product name, technology, service, or version.
- Never select a capability unsupported by the supplied evidence.
- Never classify target_profile as LINUX_HOST or WINDOWS_HOST unless direct OS-identifying evidence is present (e.g. OS banners, TTL/OS fingerprint results, an OPERATING_SYSTEM_IDENTIFICATION finding). If a host is reachable but no OS evidence exists, use UNKNOWN as the target_profile.
- DO_NOT_REPEAT_COMPLETED_ACTION is a guardrail concept, not a selectable next_capability. Never return it as next_capability; instead select REQUEST_ADDITIONAL_EVIDENCE or STOP_NO_RELEVANT_ACTION when no new uncompleted action applies.
- Architecture-specific capabilities require their specific supporting evidence, not general plausibility. Never select DIRECTORY_SERVICE_ENUMERATION or WINDOWS_SERVICE_ENUMERATION without Kerberos, LDAP, or SMB evidence. Never select CLOUD_ASSET_DISCOVERY without cloud provider evidence (e.g. AWS/Azure/GCP metadata, S3/blob storage indicators). Never select CONTAINER_DISCOVERY without container-platform evidence (e.g. Docker/Kubernetes API responses). Never select IOT_SERVICE_IDENTIFICATION without IoT-specific protocol evidence (e.g. MQTT, CoAP, UPnP). If none of these apply, prefer a general capability (CONTENT_DISCOVERY, WEB_CRAWLING, OPERATING_SYSTEM_IDENTIFICATION, PARAMETER_DISCOVERY) that the current evidence actually supports, or STOP_NO_RELEVANT_ACTION if none remain.
- DEAD-END DOMAIN DETECTION: If the zero_findings_actions list contains PASSIVE_ASSET_DISCOVERY, SUBDOMAIN_DISCOVERY, and DNS_RESOLUTION (meaning they all ran but found nothing), then the domain is likely unreachable. Do NOT retry any of these capabilities. Select STOP_NO_RELEVANT_ACTION with target_profile UNREACHABLE.

MANDATORY GUARDRAILS (override all other rules):

- HTTPS TLS ANALYSIS GUARDRAIL: If open_ports contains 443 or 8443, OR any WEB_PROBING result used an https:// URL, AND TLS_ANALYSIS is NOT in completed_actions, you are FORBIDDEN from selecting STOP_NO_RELEVANT_ACTION -- select TLS_ANALYSIS instead. SUBDOMAIN PIVOTING RULES:

- When `subdomains` is non-empty AND `subdomain_resolutions` is empty, you need resolution data for all subdomains before making pivot decisions. If DNS_RESOLUTION has been completed for the main domain, the subdomain_resolutions data should be available. If it is not, select DNS_RESOLUTION to begin resolving subdomains.

- After `subdomain_resolutions` is populated, analyze the results. Compare each subdomain's resolved IP against `resolved_ip` (the main domain's IP). Subdomains resolving to DIFFERENT IPs are likely on different infrastructure and are worth investigating. Subdomains resolving to the SAME IP are likely behind the same CDN/WAF as the main domain and offer limited additional value.

- BEFORE selecting PIVOT_TO_SUBDOMAIN, check these fields in the evidence:
  * `subdomains_exhausted`: if true, ALL reachable different-IP subdomains have been investigated. Do NOT select PIVOT_TO_SUBDOMAIN. Select STOP_NO_RELEVANT_ACTION or continue parent domain recon.
  * `subtarget_results`: lists subdomains already investigated. Do NOT pivot to them again.
  * `subdomain_resolutions`: null values mean the subdomain doesn't resolve. Do NOT pivot to unresolvable subdomains.
  * `previous_observations`: look for entries containing "PIVOT_TO_SUBDOMAIN skipped" — these tell you which subdomains failed and why.

- If reachable subdomains exist with DIFFERENT IPs from the main domain AND `active_subtarget` is null AND `subdomains_exhausted` is not true, select PIVOT_TO_SUBDOMAIN. Set `next_subdomain` to the highest-value reachable different-IP subdomain NOT in `subtarget_results`. Prioritize by: (1) names suggesting management interfaces (grafana, kibana, jenkins, gitlab, prometheus), (2) names suggesting infrastructure (kubernetes, docker, consul, vault, etcd), (3) names suggesting network access (vpn, gateway, proxy, external, staging), (4) any other reachable subdomain on a different IP.

- When `active_subtarget` is set and recon is exhausted (STOP_NO_RELEVANT_ACTION for that subdomain), select RETURN_FROM_SUBDOMAIN to resume the parent domain.

- DO NOT pivot to: subdomains that fail DNS resolution (null in subdomain_resolutions), subdomains on the SAME IP as the main domain (same CDN/WAF protection), subdomains already in `subtarget_results` (already investigated), subdomains with zero open ports if port data exists.

FAILURE PATTERN AVOIDANCE:

- Check `failure_patterns` before selecting any capability. If a capability has failed 3+ times across any targets with timeout or connection errors, do NOT select it again. Select a different capability or STOP_NO_RELEVANT_ACTION.

- If CONTENT_DISCOVERY failed with timeout and technologies include Cloudflare, Cloudflare Bot Management, or similar WAF/CDN: it will timeout again. Skip it entirely.

- If HEADER_ANALYSIS failed with connection_refused and the target is behind Cloudflare: it will fail again. Skip it.

TECHNOLOGY-SPECIFIC FOLLOW-UPS (when detected on current target):

- Grafana detected -> prefer API_ENDPOINT_DISCOVERY, then HEADER_ANALYSIS, then TLS_ANALYSIS
- WordPress/Drupal/Joomla detected -> prefer CMS_ASSESSMENT
- Kubernetes/Docker API detected -> prefer CONTAINER_DISCOVERY
- OpenAPI/Swagger detected -> prefer API_ENDPOINT_DISCOVERY, then PARAMETER_DISCOVERY
- React/Angular/Vue SPA detected -> prefer JAVASCRIPT_ANALYSIS, then WEB_CRAWLING
- Cloudflare/Akamai/CloudFront detected -> skip CONTENT_DISCOVERY and HEADER_ANALYSIS on this target; focus on subdomain pivoting to find origin servers
- Mail server software detected (Postfix, Exchange, Zimbra) -> prefer DNS_ENUMERATION, then HEADER_ANALYSIS
